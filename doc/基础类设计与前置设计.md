## 3. 当前版本的核心业务定义

这一版产品先围绕最小可闭环流程展开：

1. 打开图片文件夹，生成项目
2. 浏览图片列表
3. 对单张图片给出处理结论
4. 给图片选择一个分类
5. 可选填写备注
6. 在筛选页按结论、分类、备注查看结果
7. 在结果页查看整体统计并导出

当前版本先固定以下分类：

- `AI 生成图`
- `设计稿截图`
- `活动素材`
- `参考图`

当前版本先固定以下处理结论：

- `通过`
- `待定`
- `淘汰`

## 4. 核心数据对象设计

这一层最重要。页面、状态管理、导入导出、持久化都应该围绕这套对象来展开。

### 4.1 项目对象 `ReviewProject`

表示一个图片评审项目。

建议字段：

```ts
type ProjectId = string
type AssetId = string

interface ReviewProject {
  id: ProjectId
  name: string
  sourceFolder: string
  coverAssetId?: AssetId
  createdAt: string
  updatedAt: string
  lastOpenedAt?: string
  assetCount: number
  version: number
}
```

职责：

- 表示项目本身
- 不直接塞入大量图片详情
- 主要用于首页项目书架、项目切换、项目元信息保存

### 4.2 图片对象 `ImageAsset`

表示被评审的单张图片基础信息。

建议字段：

```ts
type ReviewDecision = 'approved' | 'pending' | 'rejected' | 'unreviewed'
type AssetCategory = 'ai-generated' | 'design-screenshot' | 'campaign-material' | 'reference'

interface ImageAsset {
  id: AssetId
  projectId: ProjectId
  filePath: string
  fileName: string
  fileSize: number
  width?: number
  height?: number
  createdAt?: string
  modifiedAt?: string
  thumbnailPath?: string
}
```

职责：

- 只描述图片的客观信息
- 不承载审核结果
- 便于后续做缩略图缓存、图片扫描、导入匹配

### 4.3 图片评审记录 `AssetReview`

表示一张图在当前项目中的审核结果。

建议字段：

```ts
interface AssetReview {
  assetId: AssetId
  projectId: ProjectId
  decision: ReviewDecision
  category?: AssetCategory
  comment: string
  reviewedAt?: string
  updatedAt: string
}
```

职责：

- 处理结论
- 分类
- 备注
- 是审核页、筛选页、结果页的核心数据来源

说明：

- `ImageAsset` 和 `AssetReview` 必须拆开，不建议混成一个大对象
- 因为图片客观信息和审核结果本质上是两类数据，拆开后更利于导入导出、缓存、覆盖更新

### 4.4 项目统计对象 `ProjectSummary`

结果页和首页项目卡片都会用到。

建议字段：

```ts
interface ProjectSummary {
  totalCount: number
  reviewedCount: number
  approvedCount: number
  pendingCount: number
  rejectedCount: number
  commentedCount: number
  categoryCounts: Record<AssetCategory, number>
}
```

职责：

- 首页卡片进度展示
- 顶部进度条
- 结果页统计图

## 5. 视图层组合对象设计

页面真正渲染时，通常不会直接用原始对象，而是会组合成“可展示对象”。

### 5.1 图片展示项 `AssetViewModel`

```ts
interface AssetViewModel {
  asset: ImageAsset
  review: AssetReview
  displayName: string
  resolutionText: string
  hasComment: boolean
  decisionText: string
  categoryText: string
}
```

职责：

- 给缩略图列表、审核页右侧、筛选结果卡片直接使用
- 避免把展示文本转换逻辑写散在各个 Vue 组件里

## 6. 基础类与服务设计

这里的“类”不一定强制要求全部写成 `class`，也可以是 service / repository / mapper。
但职责必须明确。

## 6.1 `ProjectRepository`

职责：

- 读取项目列表
- 保存项目元信息
- 删除项目记录
- 更新最近打开时间

建议方法：

```ts
interface ProjectRepository {
  list(): Promise<ReviewProject[]>
  getById(projectId: ProjectId): Promise<ReviewProject | null>
  save(project: ReviewProject): Promise<void>
  remove(projectId: ProjectId): Promise<void>
}
```

## 6.2 `AssetRepository`

职责：

- 保存图片基础信息
- 查询某个项目下的所有图片
- 按图片 id 获取详情

建议方法：

```ts
interface AssetRepository {
  listByProject(projectId: ProjectId): Promise<ImageAsset[]>
  saveAll(projectId: ProjectId, assets: ImageAsset[]): Promise<void>
  getById(assetId: AssetId): Promise<ImageAsset | null>
}
```

## 6.3 `ReviewRepository`

职责：

- 读取和保存审核记录
- 按项目批量取回所有审核结果
- 更新单张图片审核信息

建议方法：

```ts
interface ReviewRepository {
  listByProject(projectId: ProjectId): Promise<AssetReview[]>
  getByAssetId(projectId: ProjectId, assetId: AssetId): Promise<AssetReview | null>
  save(review: AssetReview): Promise<void>
  saveMany(reviews: AssetReview[]): Promise<void>
}
```

## 6.4 `ProjectScannerService`

职责：

- 扫描本地文件夹
- 识别支持的图片格式
- 生成 `ImageAsset`
- 初始化默认的 `AssetReview`

建议方法：

```ts
interface ProjectScannerService {
  scanFolder(folderPath: string): Promise<ImageAsset[]>
  createProjectFromFolder(folderPath: string): Promise<{
    project: ReviewProject
    assets: ImageAsset[]
    reviews: AssetReview[]
  }>
}
```

## 6.5 `ProjectSummaryService`

职责：

- 根据图片和审核记录计算统计信息
- 给首页、顶部、结果页统一提供统计结果

建议方法：

```ts
interface ProjectSummaryService {
  buildSummary(assets: ImageAsset[], reviews: AssetReview[]): ProjectSummary
}
```

## 6.6 `FilterService`

职责：

- 根据筛选条件过滤图片
- 支持状态、分类、是否有备注、关键字搜索

建议方法：

```ts
interface ReviewFilter {
  decision?: ReviewDecision[]
  category?: AssetCategory[]
  hasComment?: boolean
  keyword?: string
}

interface FilterService {
  filter(items: AssetViewModel[], filter: ReviewFilter): AssetViewModel[]
}
```

## 6.7 `ExportService`

职责：

- 导出结果包
- 导出结果清单
- 导出结果报告

建议方法：

```ts
interface ExportService {
  exportResultPackage(projectId: ProjectId): Promise<void>
  exportAssetList(projectId: ProjectId): Promise<void>
  exportReport(projectId: ProjectId): Promise<void>
}
```

## 7. 前端状态管理建议

当前项目已经有 `pinia` 依赖，建议尽快明确 store 结构。

### 7.1 `projectStore`

负责：

- 当前项目信息
- 项目列表
- 当前项目统计摘要

### 7.2 `assetStore`

负责：

- 当前项目下的图片列表
- 当前选中图片 id
- 缩略图列表展示数据

### 7.3 `reviewStore`

负责：

- 当前项目的审核记录
- 单图修改
- 自动保存状态

### 7.4 `filterStore`

负责：

- 筛选页条件
- 当前筛选结果

建议原则：

- 页面组件不要直接负责复杂业务状态
- “图片基础信息”和“审核结果”不要混在一个 store 的同一个对象里乱改
- 所有保存入口尽量收口到 store action 或 service 中

## 9. 页面开发前必须先完成的基础工作

这部分建议优先于页面样式开发。

### 9.1 先定义共享类型

必须先落地：

- `ReviewDecision`
- `AssetCategory`
- `ReviewProject`
- `ImageAsset`
- `AssetReview`
- `ProjectSummary`

如果这些类型不先统一，后面每个页面都可能自己发明字段名。

### 9.2 先定义分类和状态常量

建议单独放到常量文件中：

```ts
export const REVIEW_DECISION_OPTIONS = [...]
export const ASSET_CATEGORY_OPTIONS = [...]
```

这样页面、筛选、导出、结果页可以共用一套配置。

### 9.3 先约定存储格式

在开始写实际持久化前，先定一个结果包结构。

建议：

```ts
interface ProjectSnapshot {
  project: ReviewProject
  assets: ImageAsset[]
  reviews: AssetReview[]
}
```

这会直接影响：

- 本地项目保存
- 导入导出
- 项目恢复

### 9.4 先准备路由骨架

建议至少先把以下页面路由搭出来：

- `/`
- `/project/:projectId/review`
- `/project/:projectId/filter`
- `/project/:projectId/result`

即使页面先是空壳，也要先把主路径定下来。

### 9.5 先准备 IPC 边界

Electron 项目后面一定会涉及：

- 选择文件夹
- 扫描文件
- 读取图片元信息
- 保存项目文件
- 导出结果

这些能力建议尽早设计成 IPC 接口，不要后面把 Node 文件系统逻辑直接塞进 Vue 页面里。

## 10. 第一阶段建议开发顺序

为了降低跑偏风险，建议按下面顺序推进：

### 第一步：模型和常量

完成：

- 类型定义
- 状态常量
- 分类常量
- 路由骨架

### 第二步：假数据驱动页面

完成：

- 首页
- 审核页
- 筛选页
- 结果页

先用假数据把页面逻辑跑通，不急着接真实文件系统。

### 第三步：项目扫描与真实数据接入

完成：

- 打开文件夹
- 扫描图片
- 生成项目对象
- 生成默认审核记录

### 第四步：持久化

完成：

- 项目保存
- 审核记录自动保存
- 项目恢复

### 第五步：导入导出

完成：

- 结果包导出
- 结果包导入
- 合并 / 覆盖策略

## 11. 当前最容易跑偏的点

### 11.1 页面先做太细，模型没定

风险：

- 页面能画出来，但状态字段各不统一
- 后面一接真实数据就要大改

结论：

- 先定类型，再写页面

### 11.2 图片对象和审核对象混在一起

风险：

- 导入导出不清晰
- 状态更新容易污染原始图片信息

结论：

- `ImageAsset` 和 `AssetReview` 必须拆开

### 11.3 过早引入复杂分类或自由标签

风险：

- 当前版本的简单流程被打散
- 筛选页和结果页复杂度瞬间上升

结论：

- 当前版本先固定 4 个分类，不开放自由 tag

### 11.4 页面文案和状态值不统一

风险：

- 页面写“通过”，数据写“pass”，导出又写“approved”
- 后期维护困难

结论：

- 内部值统一英文枚举，界面统一中文文案

## 13. 结论

正式开发前，最关键的不是马上把页面写满，而是先固定这三层：

- 业务对象：项目、图片、审核记录、统计
- 服务边界：扫描、保存、筛选、导出
- 页面基线：审核页只围绕结论、分类、备注展开

只要这三层先定稳，后面继续做首页、审核页、筛选页、结果页，就不容易越做越偏。
